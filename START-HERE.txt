ORANGE PI DEPLOYMENT
See docs/orange-pi-deployment.md for Apache/PHP/MariaDB, migrations, kiosk setup,

RUN IN XAMPP
1. Keep the project in C:\xampp\htdocs\MediVend.
2. Start Apache and MySQL in the XAMPP Control Panel.
3. Use the existing medivend_db database. For a fresh machine, import the
   original medivend_db.sql through http://localhost/phpmyadmin/.
4. Check config/database.php:
   localhost | port 3306 | medivend_db | root | empty password.
   Apply the additive event-ledger migration and current-price update:
   & 'C:\xampp\php\php.exe' scripts/migrate.php
5. Open http://localhost/MediVend/ rather than opening index.html directly.
6. Get Started > choose items > Review order > acknowledge demo > Save order.
7. Demo payment shows the reference, total, amount inserted, balance, and coins.
8. Use Demo insert PHP 1 / PHP 5 / PHP 10 / PHP 20. No real coins are accepted.
9. After Demo payment complete, choose Simulate dispensing.
10. Simulate each confirmed unit, a jam, or no sensor confirmation.
11. After every unit is confirmed, tap Finish session before the next customer.

CATALOG
api/products.php reads active products. Names, descriptions, stock and prices
come from MySQL. All three current medicines are PHP 10 per unit (1000 centavos).
The SQL price update leaves previous order totals and item snapshots unchanged.
Image paths are local, with bundled
photos/placeholders for null or broken paths. Loading/error/retry states and
the centered, continuously animated welcome screen are preserved.

SAVING AN ORDER
- JavaScript posts only product IDs and quantities to api/checkout.php.
- A separate Idempotency-Key header identifies the same request on retries.
- PHP validates integer quantities, active products, and current stock.
- Prices, names, and compartments are read and snapshotted from the database.
- One database transaction saves transactions plus transaction_items.
- Any failure rolls back every write. Validation errors keep the cart editable.
- Repeated taps and concurrent retries create one order per request key.
- The same request returns the original reference, snapshots, and total.

IF SAVING CANNOT BE CONFIRMED
Your cart and request key are kept in this tab's session storage. Use Retry
save to check/save the same order. Reloading the tab restores an unconfirmed
checkout. Editing and starting over are temporarily disabled while its result
is uncertain; retrying prevents a second order after a lost response.

DEMO PAYMENT AND DISPENSING
Every new order is a demo with payment_status=pending, amount_paid_centavos=0,
dispensing_status=not_started, order_status=pending, completed_at=NULL, and
item dispensed_quantity=0. Saving does not reserve or reduce stock.
Demo coins update amount_paid_centavos in integer centavos. Payment becomes
partial or paid; overpayment is rejected because this demo has no change.
Display: Exact payment only. This machine cannot return change.
Only simulated events are rejected;
physical coin rejection/return capabilities have not been verified.
The new demo_coin_events ledger stores unique event IDs and accepted/rejected
results. Ledger insertion and credit updates use one database transaction.
Duplicate retries replay the stored result, without adding another credit.
Different simultaneous events are checked against the saved remaining balance.
Migration 003 adds PHP 20 support and labels existing ledger events as demo.
Demo buttons larger than the remaining balance disable; PHP also rejects them.
This does not inhibit physical coins. includes/accepted-coin.php is a server-only
recorder with no public route or hardware connection. Simulated tests verify that
money already accepted is recorded in full, including excess. Excess/out-of-stage
credit flags needs_review and stops automatic dispensing, preserves credit and
partial deliveries, and requires staff. No change or refund is claimed.
Keep hardware disconnected until rejection/inhibit capabilities are verified.
Only fully paid demo orders may start the dispensing simulation. Stock is
rechecked before starting and before each confirmed unit.
Each confirmed simulated unit atomically decreases demo product stock and
increases the item's dispensed_quantity. Duplicate state-bound events cannot
count twice. Completion requires every unit to be confirmed.
Jam or no sensor confirmation stops with needs_review and the message
Please contact clinic staff. Partial deliveries are preserved. No automatic
retry or refund is claimed. Real stock (is_demo=0 products) is not consumed.
The saved reference is not proof of real payment or physical delivery.
After credit is inserted, Start over/home opens staff assistance and keeps the
current order and credit. There is no credited-order cancellation or refund
action. Start over closes an unpaid saved session through PHP under the same
lock as coin events. A concurrent coin either prevents closing or is rejected
after closing. Saved rows remain. Credited or unresolved orders cannot close.
After complete confirmed delivery, Finish session clears customer browser state
and returns to welcome. Unresolved sessions never clear on an automatic timer.

The current order and credit recover on reload or reopening a tab in the same
browser. Pending coin IDs/denominations are kept before sending. Retry same
demo coin event resends that ID safely; Refresh status checks the ledger first.
The animation alone never counts a coin. Refresh status reads recorded delivery
counts after an uncertain result, then flags an incomplete run needs_review via
no_confirmation. Confirmed units remain; no delivery is repeated. A completed
order remains completed. Failed status/stop requests keep the error visible.

TEST
From PowerShell in this folder, with Apache/MySQL running:
& 'C:\xampp\php\php.exe' tests/products-api.test.php
& 'C:\xampp\php\php.exe' tests/checkout-api.test.php
& 'C:\xampp\php\php.exe' tests/demo-flow-api.test.php
& 'C:\xampp\php\php.exe' tests/coin-payment-api.test.php

The checkout test creates and removes its own temporary products/orders and
checks validation, snapshots, rollback, authoritative prices, and concurrent
retry protection. It does not change existing products or stock.
The simulation/coin tests use their own temporary data and check mixed coins,
multiple items, durable duplicate replay, concurrent events, refresh lookup,
overpayment, payment completion, stock updates, jams, and missing confirmation.
They also check concurrent payment versus unpaid-session closing.
PHP 20 tests cover exact PHP 20 orders, all four denominations mixed, rejection
on PHP 10 orders, overpayment after partial credit, persistent replay/reload,
and simulated already-accepted excess credit with staff review.

An optional full touch-browser audit is tests/purchase-flow-browser.test.mjs.
It requires Node.js, an available Puppeteer module and Chrome. See README.md for
the command. It uses isolated test inventory, saves screenshots in a temporary
folder, removes owned fixtures, and verifies existing database rows are unchanged.
See docs/purchase-flow-audit.md for results and remaining manual checks.

MANUAL CHECK
Two Paracetamol and one Cetirizine now total PHP 30.00 for a new order.
Save the order and find its reference in transactions in phpMyAdmin. Check the
item snapshots in transaction_items, pending/not_started statuses, zero paid
and dispensed values, and unchanged stock in products.
Then simulate two PHP 10 + one PHP 5 + five PHP 1 coins. Check paid status and
3000 inserted centavos. Check eight accepted rows in demo_coin_events.
Before completion, press Start over and verify credit is preserved with a
staff-assistance path. Try a coin larger than the remainder to see guidance
for smaller simulated denominations. New events after full payment fail.
Manual confirmed-delivery tests consume demo stock; use demo test inventory.
For a connection failure, stop MySQL after reaching review, save, restart
MySQL, and Retry save. The cart and original request key are preserved.

Use 1024 x 600 landscape, 100% display scaling/browser zoom, and F11 full screen
for the intended touchscreen layout. Apache and MySQL must keep running.
